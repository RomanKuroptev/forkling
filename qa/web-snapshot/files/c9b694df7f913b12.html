Derivative Ideas

Ideas based on other languages.

  • BCDFuck: A brainfuck variant where the input is in BCD, except that the unused six states of 4-bit BCD encoding are interpreted as brainfuck-like instructions while 0-9 are stored directly in the cells as they are entered.
  • A BitBitJump variant using variable-length addresses. For example, each address bit except the last one could be succeeded by a 1, while the last address bit would be succeded by a 0 as an end marker. This means that addresses can be arbitrarily large, possibly making BBJ Turing complete.

Interactive theorem provers

  • In the standard Curry-Howard-Lambek correspondence, propositions correspond to types and proofs correspond to programs. The idea is to create a theorem prover where propositions are programs and proofs are optimizations for those programs. Each provable proposition will eventually reduce to the constant True. Without a proof, the prover will try every possible combination of inference rules. A proof merely tells the prover which combination of inference rules to try first. Even though proofs are optional, verifying a proposition without them would require exponential time complexity.
  • A theorem prover without definitions. Each expression is a tree with built-in terms at its leaves. Every node is unique, and users may assign names to nodes, though these names are purely conventional. The prover maintains a map of ordered pairs of expressions to their unique identifiers. When constructing a new expression from two previously constructed expressions, the prover checks whether this ordered pair exists in the map. If it does, the prover returns the existing identifier; otherwise, it inserts the pair and assigns a new identifier.
  • A theorem prover that uses reduction rules instead of inference rules. There are a few built-in terms and a few built-in reduction rules. When a user wants to prove a theorem, they write an expression by combining previously defined terms. The prover then reduces the expression according to the current reduction rules. Once a normal form is reached, it represents the proposition that the user has proved. If this resulting proposition has the form of a reduction rule, that rule is added to the set of reduction rules and used for subsequent theorems.
  • A theorem prover designed to be maximally fast and efficient. The kernel supports only very basic inference rules. However, it contains the definition of x86-64 machine code semantics and is implemented in this machine code. The user can construct a new prover within the system. Once the user proves that the machine code representing the new prover is equi-consistent with the old prover (meaning everything provable in the new prover is also provable in the old prover), the system then replaces its original machine code with the new machine code. This concept is similar to that of the Milawa prover, but more generalized.
  • A theorem prover for reasoning about computable functions. Axioms are represented as assertions that certain functions terminate. A theorem is a proof that a certain function terminates. Proofs are constructed using induction. Induction is performed on the termination of functions corresponding to axioms and other theorems. Data structures are represented by functions that traverse a raw tree and terminate only if the tree has a particular structure.
  • A theorem prover that uses only local identifiers. Global definitions and theorems are introduced as lambda expressions, making them effectively local. Identifiers are represented as either de Bruijn indices (where 0 references the most nested lambda) or de Bruijn levels (where 0 references the least nested lambda), but there is no practical distinction between "global" and "local". The kernel only works with de Bruijn indices, and the elaborator converts levels to indices before passing proofs to the kernel.
  • A set-theoretic theorem prover with "dependent" sets. Everything is a set. There exists a very large built-in set called The Universe, which contains all sets of interest. For each natural number, there is a corresponding type universe (which is itself a set). All type universes belong to The Universe. Each type universe contains concrete types specific to that universe. A type universe corresponds to what is called Sort u in Lean, where u is the associated natural number. Every type is also a set. Most types of interest belong to type universe 1; examples include natural numbers, lists, trees, trigonometric functions, and geometric shapes/bodies. The list datatype itself (when not parameterized by any specific type) belongs to type universe 2. Polymorphic functions, such as equality, belong directly to The Universe. We reason about polymorphic functions only in polymorphic contexts and cannot directly analyze their polymorphism. The user may introduce axioms that dictate the actual size of The Universe.
  • A theorem prover with no source code or refactoring. Users interact with the prover by applying inference rules as actions and assigning the resulting theorems to global identifiers. The identifiers exist only in the user interface, not within the prover itself. When a user wants to change a definition or a theorem statement, they simply create a new one rather than editing existing structures. After changing a definition, the user either manually proves the relevant theorems for the new definition or supplies a program that does so automatically.
  • A centralized theorem prover hosted on a public server. Each client request applies an inference rule, producing a new theorem (or an error). All requests that yield a valid new theorem are permanently stored together with the theorem statement. Everything is publicly visible. As in the previous idea, there is no source code or refactoring. Client requests may also contain programs that prove theorems; each such program has limited execution time and memory.
  • A prover based on a hierarchy of computable functions. The idea is to have an untyped lambda calculus extended with an equality construct. Every expression is either an identifier, a lambda abstraction, an application, or an equality of two expressions. Every expression resides in a universe. There is a universe for every natural number. Universe 0 corresponds to the semicomputable functions. The arguments of an equality must be expressions from the same universe, and the resulting equality expression belongs to the next higher universe. In universe 0, no equality expressions are allowed. In universe 1, equalities may compare expressions from universe 0. In general, in universe n, equality expressions may involve subexpressions from any universe less than n. An equality expression reduces in a single step: it evaluates to the Church boolean true (λ x y, x) when the two sides are identical, and to false (λ x y, y) otherwise. Quantifiers can be expressed using equality. For example, ∀ x, P x can be encoded as P = (λ x, true).
  • A prover based on type casting rather than type enforcement. Instead of requiring a function argument to have a certain type, the system dynamically casts it to the expected type. Every type is inhabited. Casting is idempotent: if the value already has the given type, casting has no effect. The behavior of casting a value that does not already have the target type is not explicitly specified, except that the result must always be of the expected type. For example, the implication P → Q does not require P and Q to be propositions; rather, it converts them to propositions. We may have a theorem of the form Prop(Prop(P) → Prop(Q)) === (P → Q), meaning that implication converts its arguments to propositions and returns a proposition. One corollary is that, instead of theorems like (True → P) === P, we must have (True → P) === Prop(P).
