## R1 fix: sketches lost as "the model gave no usable answer" (18 November)

The R1 fast-forward (main at 7033303) lost 8 of 28 sketches (from 20 November on, 8 of 13) with this note, among them every sketch on 22 and 25 November. Each call was whole (about $0.01 to $0.024 on Sonnet, far under the 10,000-token limit, stop reason neither `refusal` nor `max_tokens`), so the JSON came back and failed the Zod check. Cause: the SDK's `zodOutputFormat` (`@anthropic-ai/sdk` 1.3.0) does not keep `enum` or `const`; it writes them into the description as text (`"{enum: [\"art\",\"game\",...]}"`), so the API never held the model to them. A sketch's `meta.kind` outside the six (the ideas then were "toys" and "sketches") parsed as nothing. This held for every enum in every call the mind makes, plan verbs included.

Fix (`apps/mind/src/llm.ts`): `outputFormat(schema)` runs the SDK's own transform and puts each `enum` and `const` back where the zod schema has them (the API supports both); `requestParams` sends it. An answer that does not fit now carries `parseError` (not JSON, or the first three issues), and the tinker note shows it: "the model gave no usable answer (meta.kind: ...)". No prompt text, retry, limit or effort changed. Tests in `test/llm.test.ts` and `test/tinker.test.ts`. The cause is inferred from the costs and the schema sent: the tick log does not keep the answers, so the next fast-forward's notes are the check.

## R1 fix: a tick crashed on a scrap with an empty about (18 November)

The R1 fast-forward rerun (main at f4229af) failed on one crash, at 2026-11-21T13:42:30, the end of a tinker step (a sketch): `tick: [... "too_small", path ["about"] ...]`. Everything else passed (something visual every day, 0 rails broken, $1.03 of $3). Cause: the model's answer had an empty (or blank) `about`. The output schema `WorkMetaDraft` has no minimum, so it parsed; `runTinker`'s check turned it down ("the title and the about must not be empty"), and a sketch's first failed check is a scrap, so `meta()` called `WorkMeta.parse` with `about: ''` (the stored meta wants 1 to 200) and threw out of the tick. A full work did the same when its repair was empty too. Seven or more meme sources (the meta keeps 6) went the same way.

Fix (`apps/mind/src/builds/tinker.ts`): `meta()` uses `safeParse`; an answer that cannot make a meta even as a scrap is `failed` with "the model gave no usable answer (about: ...)" (the first three issues), as an answer that did not parse is. No retry and no new rule: a full work still gets its one repair for an empty about, and is shelved if the repair mends it. The output schema is unchanged: `.min(1)` there would go out as `{minLength: 1}` in the field's description (the SDK's transform writes unsupported keywords into it), which is prompt text. The other draft fields were checked against `WorkMeta`: title, interest and the constraint refusal are clamped by code, kind is an enum the API now enforces, and sources were the one other mismatch. Tests in `test/tinker.test.ts`.

## R1 fix: mornings and a decide cut off at the output limit (18 November)

The R1 fast-forward rerun (main at 8039a61) had 5 cut-off calls: mornings on 22 and 23 (twice) November and a decide on 25 November, each stopped at `max_tokens` (3,000, the default in `ask.ts`). Cause: the limit, not #231 or #232. The decide and morning code was the same in the run before (f4229af, which already had both) and in this one (#233 touched only tinker). The ledgers show the output creeping up to the limit in every run: morning median 2,004 / 2,170 / 2,311 tokens, maximum 2,985 / 2,985 / 3,000 in the three runs. This run asked 149 decides (lane A's rejection loop) against 66 to 84, so it drew more of the tail. Decide and morning are Haiku at medium effort, so they think, and the thinking is billed as output. The answer is about 1.5K, as spec 13 says. Tend had the same fault at 1,500: 5 of its 37 calls stopped there.

Fix: `DECIDE_MAX_TOKENS = 6000` in `tick/ask.ts` (the default for decide and morning, the only callers that use it) and `TEND_MAX_TOKENS = 3000` (twice its 1.5K answer in spec 13, the spec's rule for calls that think). A finished answer costs only what it uses. The guard's estimate before a call goes up by at most $0.0015 for decide and $0.00075 for tend. No prompt text. Tests are in `test/ask.test.ts`.

The back-off is not changed. It is spec 2.3: "After a failed call, all triggers except `newDay` wait 30 minutes". `route.ts` notes "not asking again yet" on every 10-second tick of that wait, about 180 notes per failure. 328 notes means two waits (22 November 07:04 and 25 November 20:13), not a lost day. A failed morning is asked again on the next tick (`newDay` is exempt), and on the 23rd the third try got a plan.

## Fix: the sandbox runner never ran under its unit (18 November)

The step 3 runbook on v0.17.0: the sandbox proof failed 7 of 8 with "no answer: is forkling-sandbox.socket running, and is the runner deployed?", and each `forkling-sandbox@N` run ended within a second, exit 0, nothing on stderr. Cause: the runner's entry check compared `fileURLToPath(import.meta.url)` with `process.argv[1]` as given. The unit starts `/opt/forkling/sandbox/current/runner.ts`, `current` is a symlink to `releases/<tag>`, and Node resolves symlinks for the main module, so the two paths differed, `main` never ran, and the process ended with no answer.

Fix (`apps/mind/src/builds/sandbox-runner.ts`): `isProgram()` compares both paths after `realpathSync`; a run that ends before its answer is written says "runner: ended (code N) without writing an answer" on stderr (the journal). `sandbox-proof.ts` had the same check and gets the same comparison (it ran from the real engine path, so it was not hit). Test: `test/sandbox-runner-entry.test.ts` lays the runner out as deploy.sh does (a release folder with `package.json` type module, `current` a symlink to it), runs it through `current` with a request that does not parse (no browser), and expects the `failed` answer; and expects the usage error on stderr without arguments. Both failed before the fix. Checked and not a fault: `watchdog.ts` runs from the checkout in the workflow (no symlink); the runner has no syntax type stripping refuses; `mkdirSync(scratch/tmp)` is in `ReadWritePaths`; `playwright-core` resolves from the real release folder.

## Fix: runs after the first came back empty (18 November, v0.17.1)

The proof's second run (v0.17.1): the first probe passed, then 6 of 8 failed with no answer at once ("after 0 s", `crashed true`, errors `[]`, probes "no probe answer"); only the image page got through. Cause, from the code and the unit: the socket has `Accept=yes` and `MaxConnections=1`, and systemd counts a connection until its service instance is gone, `ExecStopPost` and Chromium's leftover processes included. The proof asks again the moment an answer arrives, so the next connection came while the last unit was still stopping; systemd accepted it and closed it at once ("Too many incoming connections (1), dropping connection" in the socket unit's journal, not the instances'). The client read a connection that ended with nothing as a run killed early, so a crash at 0 s. One got through when the last unit happened to be gone already.

Fix: the runner writes `ready` before it reads (`READY` in `sandbox-runner.ts`); the client (`exchange` in `sandbox-run.ts`) treats a connection that ends or breaks with nothing written as the unit being busy and tries again every 300 ms for up to 20 s, then says "the sandbox stayed busy" (unavailable, never a crash). A run's time counts from `ready`. `createSocketSandbox` keeps `lastProblem()` (no answer, the runner's own `failed` words, a wrong shape), and `sandbox-proof` adds it to every failing line and prints `crashed` and `timedOut` for the page that draws. The unit files are unchanged. Tests in `test/sandbox-socket.test.ts`, `test/sandbox-proof.test.ts` and `test/sandbox-runner-entry.test.ts`.
